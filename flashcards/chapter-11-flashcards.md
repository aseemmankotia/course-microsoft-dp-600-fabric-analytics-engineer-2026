## Chapter 11: DAX, Calculation Groups, Performance Tuning & Model Security — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What triggers context transition in DAX? | Any measure reference evaluated inside a row context (e.g., inside an iterator, or a calculated column). DAX implicitly wraps it in CALCULATE, converting row context into filter context. Exam tip: this is why SUMX([Measure]) can behave differently than expected. |
| 2 | CALCULATE vs FILTER — which causes context transition? | CALCULATE (and CALCULATETABLE) perform context transition. FILTER is just a table iterator passed as an argument and does not itself cause transition. |
| 3 | What is a calculation item? | An individual formula (e.g., YTD, PY) defined inside a calculation group, applied dynamically to whichever base measure is placed on a visual. Exam tip: calculation groups replace dozens of duplicate time-intelligence measures. |
| 4 | How many calculation groups can precedence conflicts occur between? | When multiple calculation groups exist, each has a Precedence property (integer) controlling which applies first if a measure intersects with items from more than one group. |
| 5 | What are the two required incremental refresh parameters? | RangeStart and RangeEnd — must be datetime type, used in a filter step on the table's date column. This exact naming is required for the Manage Incremental Refresh dialog to activate. |
| 6 | Incremental refresh: what does 'Detect data changes' do? | Uses a specified column (e.g., LastModified) to refresh only partitions with changed rows, avoiding full reprocessing of unchanged historical partitions. Reduces refresh time and capacity usage. |
| 7 | What is the #1 driver of Vertipaq column storage size? | Column cardinality (number of distinct values). High-cardinality columns compress poorly under dictionary/RLE encoding. Exam tip: remove unused high-cardinality columns (e.g., GUIDs, transaction IDs) not used in relationships or analysis. |
| 8 | Which Vertipaq encoding works best on sorted, low-cardinality columns? | Run-Length Encoding (RLE). It compresses repeated consecutive values efficiently — sorting data by low-cardinality columns before load improves RLE effectiveness. |
| 9 | Aggregation tables: what mode combination enables the 'DirectQuery detail, Import aggregation' pattern? | A composite model where the aggregation table is Import mode and the detail fact table is DirectQuery. Power BI automatically routes queries to the aggregation table when possible (query matches GroupBy columns), falling back to DirectQuery detail otherwise. |
| 10 | Dynamic RLS — key DAX function used? | USERPRINCIPALNAME() (or USERNAME()) compared against a Users table column, filtering fact/dimension tables via relationships. Exam tip: dynamic RLS scales without creating one role per user. |
| 11 | OLS vs RLS — what's the difference? | RLS filters ROWS of data per role/user. OLS (Object-Level Security) hides entire TABLES or COLUMNS from a role regardless of row filters. OLS is configured via Tabular Editor, not the native Power BI Desktop RLS UI. |
| 12 | Copilot for DAX in Fabric — what must the author always do? | Review and validate any Copilot-generated DAX/query before accepting it into the model. Copilot proposes based on model metadata (table/column names, relationships) but does not guarantee business-logic correctness. |

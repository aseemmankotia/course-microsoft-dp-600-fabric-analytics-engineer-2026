## Chapter 2: Securing Data: RLS, CLS, OLS, and Dynamic Data Masking — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Where is RLS defined and enforced: semantic model, warehouse, or lakehouse? | Semantic model only (Power BI). Defined via roles + DAX filter expressions in Power BI Desktop, then role membership assigned in the Service. Exam tip: RLS is NOT a T-SQL feature. |
| 2 | Static RLS vs Dynamic RLS — key difference? | Static: fixed DAX filter, e.g. [Region] = "West" — one role per value. Dynamic: uses USERPRINCIPALNAME() or USERNAME() joined to a security table so one role covers all users. Exam tip: Dynamic scales; static requires one role per filter value. |
| 3 | USERNAME() vs USERPRINCIPALNAME() in DAX RLS — which format does each return? | USERNAME() = domain\username. USERPRINCIPALNAME() = email/UPN format (used by Power BI Service). Exam tip: Mismatching function to stored format causes zero rows returned (looks like broken RLS). |
| 4 | How do you test an RLS role before publishing in Power BI Desktop? | Modeling tab → 'View As Roles', optionally enter a UPN to simulate dynamic RLS for a specific test user. Exam tip: This is the fastest validation method — no need to publish first. |
| 5 | What does Object-Level Security (OLS) hide, that RLS does not? | OLS hides entire tables, columns, or measures from a role — including from metadata/Explorer pane. RLS only filters rows; the object structure stays visible. Exam tip: OLS in semantic models typically requires external tools (e.g., Tabular Editor) or TMDL, not the standard Desktop UI. |
| 6 | T-SQL syntax to grant column-level SELECT on specific columns of a table? | GRANT SELECT ON dbo.Table(Col1, Col2) TO role_name; Exam tip: This is CLS via T-SQL, used in Warehouse or Lakehouse SQL analytics endpoint. |
| 7 | T-SQL syntax to hide an entire table (OLS) from a role? | DENY SELECT ON dbo.SensitiveTable TO role_name; Exam tip: DENY always overrides any inherited GRANT from another role membership. |
| 8 | DENY vs GRANT vs REVOKE precedence in T-SQL security? | DENY always wins over GRANT, even if GRANT comes from a different role the user belongs to. REVOKE only removes a specific prior grant/deny — it does not override permissions from other role memberships. Exam tip: Use DENY when you must guarantee no access regardless of other grants. |
| 9 | T-SQL syntax to add Dynamic Data Masking to an existing column? | ALTER TABLE Customers ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()'); Exam tip: The ADD keyword is required when masking an already-existing column — forgetting it is a common exam trap. |
| 10 | Four Dynamic Data Masking function types and their behavior? | default() — full mask based on data type (string→XXXX, numeric→0, date→1900-01-01). email() — shows first letter + XXX@XXX.com. partial(prefix,padding,suffix) — custom string mask, e.g. partial(1,"XXXXXXX",0). random(low,high) — random numeric value for numeric types. Exam tip: partial() is the only one that takes 3 parameters. |
| 11 | Who can bypass Dynamic Data Masking by default? | Members of db_owner and users with elevated admin rights can see unmasked data by default. To prevent this, explicitly DENY the UNMASK permission to that principal on the column/table. Exam tip: 'admins automatically see masked data unmasked unless denied UNMASK' is a frequently tested nuance. |
| 12 | Which Fabric items support T-SQL CLS/OLS/DDM security via GRANT/DENY? | The SQL analytics endpoint of both Warehouses and Lakehouses. Exam tip: Spark notebooks accessing Lakehouse Delta tables directly BYPASS this SQL-endpoint security — only queries through the SQL endpoint enforce it. |

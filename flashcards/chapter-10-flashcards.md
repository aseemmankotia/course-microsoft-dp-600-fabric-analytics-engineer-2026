## Chapter 10: Semantic Model Storage Modes: Direct Lake, Import, DirectQuery — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | What does Direct Lake mode do differently from Import mode? | Direct Lake reads Delta Parquet files directly from OneLake into memory on demand, with no separate ETL/copy step. Import performs a full scheduled extract into the Vertipaq cache. Exam tip: Direct Lake removes refresh lag for large Lakehouse tables. |
| 2 | Name three conditions that cause a Direct Lake table to fall back to DirectQuery. | 1) Calculated columns/calculated tables on the table, 2) exceeding row group/file guardrails, 3) the Direct Lake behavior property forced to DirectQuery, or unsupported query patterns (e.g., referencing views instead of Delta tables). Exam tip: fallback is silent by default (Automatic setting). |
| 3 | What is 'framing' in a Direct Lake semantic model? | The process of mapping the model's in-memory column data to a specific, transactionally consistent version of the Delta table's Parquet files in OneLake. Exam tip: reframing happens on refresh (scheduled or manual) — new OneLake data isn't visible until reframing occurs. |
| 4 | Default row limit returned by a single DirectQuery query to Power BI? | 1 million rows (Max Intermediate Row Set Count). Exam tip: raising this is discouraged — it increases source load and latency rather than fixing performance. |
| 5 | Scheduled refresh limit: Pro/shared capacity vs Premium/Fabric capacity? | 8 refreshes/day on Pro (shared) capacity; up to 48 refreshes/day on Premium or Fabric capacity. Exam tip: exceeding Pro's limit requires moving the workspace to Premium/Fabric capacity, not just enabling incremental refresh. |
| 6 | Approximate Direct Lake row group guardrail per table before fallback risk? | Around 1,000 row groups per table is the commonly documented threshold; exceeding it (e.g., from many small file writes) risks fallback to DirectQuery. Exam tip: applying V-Order and table optimization/compaction in the Lakehouse reduces row group count. |
| 7 | Import mode vs DirectQuery: main tradeoff? | Import = fast (in-memory Vertipaq cache) but data only as fresh as last refresh; large models consume capacity memory. DirectQuery = always live/fresh but query latency depends on source performance and has row-return limits. Exam tip: exam scenarios test choosing based on freshness vs performance requirements. |
| 8 | Direct Lake vs Import: main tradeoff? | Direct Lake gives near in-memory speed with data read straight from OneLake (no import step, low staleness) but is restricted to Delta tables in OneLake and has fallback conditions. Import supports any modeled feature (calc columns/tables) but requires scheduled refresh and duplicates storage. Exam tip: choose Direct Lake for large Lakehouse fact tables needing freshness + speed. |
| 9 | What is a composite (hybrid) model in Power BI/Fabric? | A single semantic model mixing storage modes across tables — e.g., Direct Lake fact table + DirectQuery live dimension + Import reference table. Exam tip: 'Dual' mode lets a table act as either Import or DirectQuery depending on the query context, commonly used for shared dimensions. |
| 10 | Which property controls whether a Direct Lake model is allowed to fall back to DirectQuery? | The 'Direct Lake behavior' property, with values: Automatic (default, allows fallback), DirectLakeOnly (no fallback, errors instead), DirectQuery (forces DirectQuery). Set via TMDL/XMLA or dataset settings. Exam tip: use DirectLakeOnly to diagnose why fallback is occurring. |
| 11 | What capacity type is required to use Direct Lake mode? | A Microsoft Fabric capacity (F SKU) — Direct Lake is not available on classic Power BI Pro-only (non-capacity) workspaces. Exam tip: capacity SKU size affects the row/size guardrails before fallback engages. |
| 12 | Why does V-Order matter for Direct Lake performance? | V-Order is a write-time Parquet optimization (sorting/compression) applied to Delta tables that improves Direct Lake read performance and reduces row group counts, lowering fallback risk. Exam tip: enabled by default for Fabric Lakehouse writes via Spark/pipelines. |
